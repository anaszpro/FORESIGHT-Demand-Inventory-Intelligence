## The Problem

NorthBay Living sells online across ~200 SKUs and plans inventory on gut feel and spreadsheets, with no forecasting in place. This costs them in two directions at once:

- **Stockouts** — best-selling products run out, and those sales are lost for good.
- **Overstock** — slow movers pile up, locking up cash that later gets marked down at a loss.

FORESIGHT turns NorthBay's own sales and inventory history into a weekly, SKU-level demand forecast and a stockout/overstock early-warning system, so the planning team knows what to reorder, what to clear, and what to leave alone — without needing a data scientist in the room.

## The Data

Four extracts, modelled on what a real D2C brand's exports look like — including realistic messiness (duplicates, inconsistent category labels, mixed date formats, missing values, and a few outliers), since cleaning that is part of the work:

| Table | Grain | Contents |
|---|---|---|
| `sales_daily` | 1 row per SKU per day | units sold, revenue, price, promo flag |
| `sku_master` | 1 row per SKU | category, subcategory, launch date, cost, list price |
| `calendar` | 1 row per day | week/month/season, holiday flag, promo events |
| `inventory_snapshots` | Weekly per SKU | on-hand, on-order, lead time, reorder point |

Data is **synthetic but structurally realistic** — 200 SKUs, ~2 years of daily history, generated with a fixed random seed so results are fully reproducible. Generated by `src/generate_data.py`; the dirtiness is injected deliberately (see `data/processed/data_quality_log.json` for every cleaning decision made and why).

## Setup & Run

```bash
pip install -r requirements.txt
```

Run the full pipeline in order — each stage depends on the previous one's output:

```bash
python src/generate_data.py   # synthetic dirty extracts -> data/raw/
python src/pipeline.py        # clean + unify + feature-engineer -> data/processed/analysis_ready.parquet
python src/forecast.py        # backtest baseline vs model, train final model, forward forecast
python src/risk.py            # stockout/overstock risk scoring -> data/processed/risk_scored.parquet
```

Launch the dashboard locally:
```bash
streamlit run app/app.py
```

Launch the scoring API locally:
```bash
uvicorn service.main:app --reload --port 8000
```
Endpoints: `GET /health`, `GET /skus`, `GET /forecast/{sku_id}`, `POST /forecast/batch`

**Reproducibility note:** the repo ships with `data/processed/*.parquet` and `models/lgbm_forecast.pkl` already committed (raw CSVs are excluded via `.gitignore` since they're regenerated deterministically), so the deployed dashboard and API work without re-running the pipeline. To verify reproducibility from scratch, delete `data/` and `models/` and re-run the four commands above — the same random seed will reproduce the same numbers below.

## Backtest Result — Model vs Baseline

Per the engagement's non-negotiable rule: beat the baseline honestly, on a leakage-free, rolling-origin backtest — never a random train/test split for time series.

| | Seasonal-naive baseline | FORESIGHT model (LightGBM) |
|---|---|---|
| **Average WAPE** (4 folds) | 0.461 | **0.265** |
| **Folds won** | 0/4 | **4/4** |

The model beat the baseline in every backtest fold, with ~43% lower average error. Each fold trains strictly on data before its 28-day test window (no leakage); full per-fold numbers are in `data/processed/backtest_results.json` and reproduced in `notebooks/03_model.ipynb`.

**Business impact from the current risk scoring snapshot:**
- ₹163,557 in sales-at-risk from SKUs flagged for stockout
- ₹249,063 in capital locked in SKUs flagged for markdown/clearance
- 196 Healthy · 2 Reorder Now · 2 Markdown/Clear (out of 200 SKUs)

## Key Assumptions

- The synthetic extracts are structurally representative of NorthBay's real sales and inventory behaviour (this is a simulated client engagement — see the project brief).
- Two years of daily history is sufficient to learn weekly seasonality for most SKUs; newly-launched SKUs with sparse history fall back to rolling-mean estimates rather than lag features.
- Inventory snapshots are weekly (Monday), not daily — the risk scoring uses each SKU's most recent snapshot as its current position.
- Lead times and reorder points in the inventory data are assumed accurate as provided.
- Negative `units_sold` values in the raw data are treated as data-entry errors (clipped to 0), not returns — there is no separate returns signal in the data.
- Random seeds are fixed throughout (data generation and model training) for reproducible results.
